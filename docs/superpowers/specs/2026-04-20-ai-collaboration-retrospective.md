# 用 AI 从零做一个产品——个人复盘

我没有编程基础，没有 UI 设计经验，这是我第一次从一个模糊的想法出发，独立把一个产品做上线。

---

## 一、这个产品是什么

**Self Journal（自我觉察日记）** — 已上线的 Web App：https://self-journal-kassia.vercel.app

**产品理念：**  
不是让 AI 告诉你「你的情绪是 X，你应该做 Y」。那种方式看起来很爽，但实际上是在替你思考。这个产品的核心只有一件事：**沉浸式写作**——你只管写，其他的事情尽量不打扰你。

AI 在里面做两类事：

**一是处理那些枯燥但必须有的工作**——你写「昨天下午」，它自动识别成精确时间；你写「妈妈」，它标注涉及人物；情绪标签、核心需求、事件分类，都尽量自动判断，不需要你写完再手动一个一个填。这些字段是后续统计分析的基础，但填的过程不应该打断你的思路。

**二是帮你串联你自己也可能忘掉的记忆**——你写了一件事，它可能找到三个月前你写过的类似处境，放在一起让你看；回顾信会主动帮你整理近期的状态；脉络系统追踪同一主题在不同时间点的变化。

**四个系统，复杂度不同：**

| 系统 | 做什么 | 复杂度 |
|---|---|---|
| **写作流** | 写内容 → 情绪卡片 → 可选觉察卡片 → 可选 AI 对话 → 随时退出即保存；自动识别时间/人物/事件；debounce 自动保存不丢数据 | 高——状态机 + 多卡片流转 + 本地复杂度评分 + 35 字段静默提取 |
| **回顾信** | 积累一定数量或时间后 AI 主动生成，帮你梳理这段时间的状态；有触发机制，不是每次都生成 | 中——触发策略 + 跨条目摘要索引的懒提取 |
| **脉络** | AI 生成候选脉络（同主题跨时间关联），用户可接受/忽略/删除；用户排除决定被持久记录，AI 不重复推；手动创建和 AI 推荐并存不冲突 | 高——三态状态机 + 手动/AI 混合编辑的冲突处理 + 两层召回策略（本地粗筛+AI 精筛） |
| **洞察** | 情绪趋势图、高频事件、状态分布等可视化，基于字段数据计算渲染 | 低中——数据聚合 + 图表渲染 |

核心是：自己通过记录，逐渐认识自己。AI 做的事，都是为了让「写」这件事更轻松，而不是替代「想」。

## 二、做了什么

### 技术栈

| 层 | 用的是什么 | 为什么 / 留了什么 |
|---|---|---|
| 前端 | React + Vite + Tailwind CSS v3 | 轻量、生态成熟，组件和业务逻辑分层清晰，Capacitor 套壳打包 APK 时前端代码零修改 |
| 数据库/Auth | Supabase（Tokyo）| 免费额度足够个人项目，内置 Auth 省去自建用户系统，RLS 行级权限保证多用户数据隔离 |
| AI | Gemini 2.5 Flash / Deepseek 可切换 | 两个接口在设置页随时切换，不绑死单一厂商，换模型不改代码 |
| 部署 | Vercel | 推 main 分支自动部署，dev/main 分支分离，dev 开发、main 上线 |
| 语音 | Web Speech API | 桌面 Chrome 可用，移动端方案（讯飞 API）接口已预留，切换时前端逻辑不需要重写 |
| APK 准备 | Capacitor（未做，已准备） | 现有代码已按移动端标准写：不依赖 hover、可点击元素 44px 以上、存储访问走抽象层、路由支持深度链接——套壳时不需要改现有逻辑 |

### 功能范围

**基础层：**
- 邮箱注册/登录（Supabase Auth，RLS 行级隔离）
- 5 种记录模板 + 引导文字，语音输入（桌面 Chrome），PWA 可添加桌面
- 记录列表按日期分组，多维搜索过滤（情绪/事件/标签/时间区间组合）

**觉察流（核心交互链路）：**
写完内容 → 情绪标签卡片 → 可选深度复盘卡片（5-7 张，根据情绪正负面动态调整）→ 可选 AI 聊几句 → 随时退出即保存。整个流程前进后退都流畅，没有「必须点完成」的打断感。每张卡片内容 onBlur 自动保存，不依赖手动点击。

- **本地内容复杂度评分**：写完后零 token 用关键词判断是否需要提示深入觉察，不滥用 AI
- **AI 静默提取**：对话结束后在后台提取 35 个字段，用户不等待直接返回详情页
- **AI 跨对话记忆**：rolling_summary + 用户画像存 Supabase，换设备不丢
- **AI 问题库**：AI 从预设问题库里选问题，不自由生成，减少 token 消耗也更可控

**自动识别与补全：**
- 时间自动识别——「刚刚9点10」「昨天下午」等表达直接转成精确时间戳，歧义时默认最近一个时间点
- 事件名补全——1天内用过的优先，超过1天按频次排，支持从写的内容里自动检测已知事件
- 涉及人员自动识别——写作阶段自动从文字里标注「妈妈」「男友」等人物，可编辑

**脉络与洞察：**
- **脉络系统**：AI 主动生成候选脉络（同一主题跨时间的关联记录），用户可以接受/忽略/删除。忽略的记录会被记住，AI 不会重复推荐。手动编辑优先于 AI 自动，两者不冲突
- **摘要索引的懒触发策略**：不在保存时提取，在生成回顾信或分析脉络前批量补提取，控制成本
- **洞察页**：情绪趋势图、高频事件、状态分布等可视化，基于真实字段数据渲染
- **图片上传**：支持多图，拖拽排序，延迟上传（写完一起传，不打断写作），失败有通知机制

### UI 设计方式

一开始每次让 AI 直接写 UI 代码，样式混乱，不同功能模块之间总有冲突。后来改成：先让产品 session 写好 HTML 静态原型，把布局、颜色、交互细节全确定好，代码 session 再按照 HTML 严格实现。这样两件事分开——产品能直接在浏览器里看效果、改设计，代码按图索骥，样式冲突从根本上少了。

## 三、我是怎么跟 AI 协作的

### 3.0 这些是怎么学到的

没有人教我。一开始我连 git 是什么都不知道，让 AI 解释，AI 举例子，我照着做，做错了再问。最早期基本是这个状态——遇到不懂的就直接问，AI 说什么就信什么。

慢慢觉得不对劲，开始主动找外部资料。看到一篇关于 superpowers 工具框架的技术分享，研究了一下，发现这套东西正好解决了我碰到的问题，引进来自己用。为了设计 AI 对话的引导逻辑，我专门去研究了 ACT、IFS、聚焦疗法等几个心理咨询流派，读完才敢动手设计问题库。发现 AI 给了一个懒答案、或者直接跳过流程，我会叫停，让它重来。

每次踩坑之后，我会把教训写进文档或 skill 文件，让它成为规则，而不是靠下次记住。这套东西不是一开始就有的，是一点一点被推出来的。

### 3.1 工作流从混乱到有规范

**早期：** 想到什么问 AI 什么，AI 给方案就用，AI 直接改代码也让它改。

**发现了问题：** 有一次我提了一个问题，AI 不讨论直接就改代码了。我才意识到这样下去：之前决定的东西 AI 会忘、改一个地方坏另一个地方、两个对话框对同一段逻辑理解不同……

**我的反应（原话）：** 「以后你再改代码的时候能不能不要直接改？我不是给你安装了一个 superpowers 的 skill 吗，你有用上吗？」

从这一句开始，确立了每次功能迭代的固定流程：

```
brainstorm（讨论清楚想要什么）
  → spec（把决策写成文档）
  → plan（拆成具体任务清单）
  → code（按任务执行，Task 0 强制先读文档）
  → review（架构审查）
```

每一步都有对应文档落地，不靠记忆，不靠信任。

### 3.2 用规则约束 AI

AI 默认会走捷径、会跳过流程、会只看眼前不看整体。我做了几件事来约束它：

**CLAUDE.md（项目规则文件）：**  
所有 AI 对话开始前自动读取。里面写的不是「希望」，是「不做会报错」的硬规定：分层原则（UI/业务/数据严格分离）、不硬编码、git 提交前必须先本地测试等。

**自定义 arch-review skill（架构审查工具）：**  
我参考外部分享，给这个项目定制了一份 12 阶段的架构审查清单。每次功能完成后 AI 强制跑一遍，逐项检查可维护性、可扩展性、安全性。

里面有一条规则是从真实错误里来的：  
有一次 AI agent 说某个函数「零调用可以删除」，我没有自己验证，直接写进了删除指令，结果执行时才发现是误报。从那之后，skill 文件里加了一条强制规则——**凡是「删除」操作，必须自己跑 Grep 验证，不接受 agent 的搜索结论**。一次错误变成了永久规则。

**Task 0 机制：**  
每个开发任务的第一步固定是「读 arch-context.md 和对应 spec 章节，确认理解没有偏差，再开始写代码」。不读完不能动手。

### 3.3 多个 AI 对话框互相制约

随着任务越来越复杂，我发展出了三个专职对话框：

| Session | 职责 |
|---|---|
| 产品 session | 产品框架、用户体验、心理学原理讨论，输出设计文档和「同步卡」 |
| 架构 session | 审查 spec，发现架构问题打回产品修改，更新架构上下文文档 |
| 代码 session | 按 plan 执行，Task 0 先读文档，不自行发挥 |

三个 session 互相读写同一套文档，文档是唯一可靠的信息传递层。我是唯一知道全貌的人，负责在三方之间传递决策。

## 四、三个让我意识到自己在进步的时刻

### 时刻一：第一次真正推翻重写

产品做到一半，AI 对话功能跑通了，但我用了几次之后觉得哪里不对。整理出来的问题是：

- 对话一刷新就消失了
- AI 弹出「好像有点复杂，要聊聊吗？」——我觉得这句话「像在赶我走」
- 我只是记录了一个幸福的小瞬间，AI 还在追问「有没有藏着别的感受」「你内心真正渴望的是什么」

这些不是 bug，是方向问题。整个产品的交互哲学从「AI 主导、推着用户走」改成了「用户随时可以选择停，AI 跟着走不打断」。沉浸式记录流、觉察卡片、静默提取、随时退出——都是这次推翻之后重新设计的。

### 时刻二：我的方案比 AI 给的更好

几个具体的时刻：

**AI 字段设计太简略**，我指出「认知扭曲这个字段，既需要一个选项方便统计，也需要一个文本框记录我的思考过程，你把这两个压成一个了」。AI 的回复：「你说得对，我为了精简反而把有价值的内容压掉了。」

**AI 建议实时查询数据库**，我质疑「每次输入都查一次，不会很慢吗？一次性搬过来不是更清楚？」。AI 的回复：「你说得对，我想复杂了。」

**我提出静默提取**：对话结束后 AI 在后台提取字段，用户直接跳回详情页不用等待。不打断体验、不让用户看到「处理中」的过渡状态。这个方案是我提的，AI 之前没有想到。

### 时刻三：从工具的用户到工具的设计者

我从外部技术分享里看到 superpowers 这套工具框架，引进来之后发现skills可以自定义。我给这个项目定制了 arch-review skill——写进去的不只是通用的架构审查原则，还有这个项目真实踩过的坑、真实确定的决策约束、真实加进去的规则。

它现在是这个产品专属的「架构师工作手册」，任何新 AI 对话框冷启动后读一遍，就能按照这个项目的标准工作。

## 五、一句话总结我现在的工作方式

不是「用 AI 帮我做事」，而是「我设计规则，AI 在规则里工作，规则本身也在持续迭代」。

我负责判断方向、发现问题、提出质疑、更新规则。AI 负责在规则内执行、生成选项、做我验证过的事。这个分工一旦清晰，产出的质量和可维护性都高很多。
