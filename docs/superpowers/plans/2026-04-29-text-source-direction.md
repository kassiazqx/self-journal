# Text Source Direction Plan

> **For reviewer sessions:** This is a pre-migration architecture decision note, not an implementation-ready migration plan. Review this as a “should we proceed, and under what boundaries?” document before any formal spec or execution plan is written.

**Goal:** 为 self-journal 确定下一阶段“写作输入、分段、基础样式、自动识别、搜索、AI 提取”的最稳方向：先验证所见即所得写作是否能和现有自动识别共存，再决定是否进入正式迁移，而不是直接启动全站文本系统改造。

**Architecture:** 当前项目已经有 `RichTextEditor`（Lexical）编辑态、`AnnotatedText` 只读态，以及 `content + annotations` 的旧模型。但本轮澄清后，用户真实目标不是重型富文本，而是：**用户看到的就是最终效果**，支持分段、加粗、单一高亮、单一下划线、固定几种文字颜色，同时不能破坏“时间/人物自动识别”等现有写作体验。推荐方向因此改为：**先做一个隔离的、所见即所得的最小原型；内部区分“编辑状态 / 纯文字语义 / 保存格式导出”，在原型通过前，不进入正式迁移。**

**Tech Stack:** React, existing editor shell, WYSIWYG constrained formatting, plain-text semantic extraction, exportable source format, Supabase now, future APK + local-first storage

---

## 1. 当前要解决的真实问题

这次问题的重点已经不是：

- 选 Lexical 还是 TipTap
- 选 Markdown 还是 doc JSON
- 直接定最终迁移方案

而是更前置的架构决策题：

**“所见即所得的轻量样式写作，能不能和现有自动识别、AI、搜索、未来 APK 本地存储目标同时成立？”**

用户当前明确需要：

1. 分段
2. 加粗
3. 单一高亮
4. 单一下划线（黑色即可）
5. 固定几种文字颜色
6. 用户看到的是最终效果，不是 `**`、`<mark>` 之类源码
7. 时间/人物等自动识别不能因为样式操作而闪断、撤回、再恢复
8. 未来尽量少走弯路，但这轮不接受直接重型大迁移

因此，这轮的关键不是“迁移”，而是“验证这种交互模型是否站得住”。

---

## 2. 先暂停正式迁移：为什么必须先做隔离原型

当前最危险的误区，是把“文本方向讨论”直接写成正式迁移 plan。

原因：

1. 目前还没证明“所见即所得写作 + 自动识别”是否稳定共存
2. 目前还没证明现有 editor shell 是否适合承载这种输入体验
3. 目前还没证明内部三层状态（编辑态 / 纯文字语义 / 保存格式）是否会把实现做得太重
4. 目前还没证明这种路线对 APK / Android WebView 真正友好

所以当前最稳决策是：

**先做隔离最小原型，不接 DB，不改正式保存链，不碰现有运行时逻辑。**

在这个原型没过之前，任何“正式迁移顺序”“字段删除计划”“全站统一方案”都不应被写成默认结论。

---

## 3. 原型应该验证什么，不验证什么

### 3.1 原型范围（必须严格收窄）

原型只验证 `journal_entries` 的“写作正文输入体验”，且只在隔离环境中运行：

- 不接 DB
- 不改正式保存链
- 不改 `journal_entries`
- 不改 `review_letters`
- 不改 `threads`
- 不做迁移脚本
- 不删任何旧字段

补充实现边界：

- 原型应尽量放在隔离 playground / demo 组件中完成，默认不直接改现有生产 `RichTextEditor`、`HomePage`、正式保存链的共享行为
- 如果为了验证必须复用现有组件，也应通过新增实验入口或最小包裹层接入，避免原型阶段提前污染正式链路
- 自动识别验证应尽量直接复用真实的 `detectPeopleFromText`、`inferDatetime` 等现有函数，不要只用 mock 逻辑证明“看起来可行”

原型内只验证这些能力：

1. 空行分段
2. 局部加粗
3. 单一高亮
4. 单一下划线
5. 固定颜色文字
6. 用户实时看到最终样式效果
7. 自动识别读取“纯文字语义”，不被样式操作干扰
8. 能导出保存格式（例如受限 Markdown / 受控 tag）

### 3.2 原型通过标准

满足以下条件才算通过：

1. 用户输入和样式操作顺畅，不需要看到源码标记
2. 空行分段在预览里与输入结构一致
3. 只改样式时，时间/人物识别结果不闪断、不撤回
4. 只在文字语义变化时，识别结果才真正变化
5. 导出的保存格式可逆、可预期
6. 提取出的纯文字语义足够干净，可供 AI / 搜索 / 摘要使用
7. 手机端 / WebView 目标环境中无明显输入和选区硬伤

### 3.3 原型失败标准

出现以下任一情况，可判定当前路线失败或至少不宜直接推进：

1. 样式操作频繁干扰自动识别
2. 编辑器实现无法清楚区分“文字变化”和“样式变化”
3. 用户体验像“在写源码”而不是在正常写作
4. 导出格式过于脆弱
5. Android / WebView 场景输入不稳
6. 实现复杂度明显超出当前产品体量

## 4. 不要再把用户编辑层理解成“直接编辑 Markdown”

这是本轮最重要的修正。

### 4.1 错误理解

错误理解是：

- 用户在输入框里实际编辑 `**加粗**`、`<mark>高亮</mark>` 这类源码
- 自动识别直接读这份源码
- 保存时再把源码落库

这种做法的问题是：

- 样式符号会打断自动识别
- 用户体验像在写源码
- 样式变化会误触发“语义变化”

### 4.2 正确理解

用户编辑层应该是：

**所见即所得的受限可视化编辑层**

也就是：

- 用户看到的是加粗效果、高亮效果、颜色效果
- 用户不看到 `**`、`<mark>`、`<span>`
- 源码格式只是系统内部导出结果，不是用户直接操作对象

这意味着：

- 保存格式可以是受限 Markdown / 受控 tag
- 但编辑过程不应等同于直接编辑这些源码

## 5. 这套模型里，到底有哪几种“文字”

为了避免概念混乱，这里明确拆成三层。

### 5.1 编辑状态（用户正在改的真实主状态）

这是用户正在操作的可视化写作状态。

特点：

- 用户看到最终效果
- 用户在这里打字、删字、选中加粗、变色
- 这是编辑过程中的唯一主状态

注意：

- 它不等于纯文本
- 它也不等于源码字符串

### 5.2 纯文字语义（给自动识别 / AI / 搜索看的干净文字）

这是从编辑状态提取出的“当前草稿语义文字”。

例如：

- 用户看到：`今` + 粗体 `早和妈` + 普通 `妈一起`
- 纯文字语义：`今早和妈妈一起`

这层用于：

- 时间识别
- 人物识别
- AI prompt 输入
- 搜索
- 列表预览

### 5.3 保存格式导出（给持久化用）

这是从编辑状态导出的保存格式。

可能形式示例：

```md
今**早和妈**妈一起
```

或：

```html
今<u>早和妈</u>妈一起
```

这层用于：

- 正式持久化
- 后续重新加载编辑状态
- 可选导出

### 5.4 三层关系

最关键的一句：

**编辑状态是主状态；纯文字语义和保存格式都是派生结果。**

不是三套并列真相。

## 6. `toPlainText()` 到底是什么，什么时候才需要它

`toPlainText()` 只是一个占位名称，意思很简单：

**把当前编辑状态或保存格式，提取成干净普通文字。**

它不是：

- 必须立即落库的一列
- 必须每次都写进数据库的东西
- 一个新的复杂系统

它本质只是：

- 一个转换函数
- 或一条纯文字提取规则

### 6.1 原型阶段怎么用

原型阶段：

- 只需要验证“纯文字语义提取”是否稳定
- 不需要正式落库存储 `content`
- 不需要接 DB

### 6.2 正式阶段才需要讨论的事

正式阶段才讨论：

- 是否把纯文字语义单独存一列
- 是否只在运行时临时提取
- 是否以后做本地搜索索引

所以当前阶段要验证的是：

**能不能稳定提取纯文字语义**

而不是：

**现在要不要立刻新增纯文本列**

---

## 7. 自动识别和样式操作怎么共存

这是当前架构里最关键的验证点。

### 7.1 不应该发生的事

如果用户写：

`今早和妈妈一起`

系统识别出：

- 时间：今早
- 人物：妈妈

然后用户把“早和妈”加粗。

此时不应该出现：

- 识别结果先消失
- 过 200ms 再重新出现

因为：

- 文字语义没变
- 只是样式变了

### 7.2 正确规则

应当明确区分两类变化：

1. **文字语义变化**
   - 打字
   - 删字
   - 替换文本
   - 这类变化才允许重跑识别

2. **纯样式变化**
   - 加粗
   - 高亮
   - 下划线
   - 颜色变化
   - 这类变化不应重跑识别

### 7.3 结论

自动识别和所见即所得写作并不天然冲突，冲突只会发生在以下错误接法中：

- 把保存格式源码直接当成识别输入
- 把样式变化误判成文字变化

因此原型里必须验证：

**样式变化不会干扰自动识别。**

## 8. 现在要不要讨论 `content` 字段怎么迁移

当前不应该把这件事写死成正式方案，但要先讲清楚三种可能。

### 8.1 方案 A：`content` 继续保持纯文本语义，另存保存格式真源

意思：

- `content` 继续给旧系统当干净文字
- 新增一个字段存保存格式真源

优点：

- 旧逻辑最稳
- 人物识别、时间推断、AI、搜索、预览改动最小

缺点：

- 多一个字段
- 保存时多一步导出

### 8.2 方案 B：`content` 改成保存格式真源，所有消费者统一提取纯文字语义

意思：

- 不再单独保留纯文本 `content`
- 旧逻辑全部改成先提取纯文字再用

优点：

- 存储更单一

缺点：

- 旧代码改动面大
- 容易漏改
- 当前阶段风险明显更高

### 8.3 当前阶段推荐结论

在原型通过前：

- **不拍板正式字段迁移**
- 但从风险角度看，正式阶段如果要推进，**A 明显比 B 更稳**

换句话说：

- 当前阶段只验证“这条路值不值得走”
- 不在这份文档里直接宣布字段迁移落法

---

## 9. 统一范围怎么定最稳

当前最稳范围是：

- **原型只碰 `journal_entries` 的写作正文体验**
- `review_letters`
- `threads`

都不进入原型实现范围。

原因：

1. `journal_entries` 是用户主动写作正文，是最值得先验证的主路径
2. `review_letters` 是 AI 生成内容，链路不同
3. `threads.current_state` 是分析结果文本，来源不同

因此：

- 终局设计可以保留“未来可能统一”的视角
- 但原型和第一阶段实施都不应从三条链同时起步

---

## 10. `annotations` 现在不要直接写成删除计划

用户已经明确表示：不需要为了“历史兼容”而勉强保留旧 annotations，只关心什么时候删最稳、bug 最少。

但即便如此，当前也不应直接写删除计划，原因不是情感保留，而是时机问题：

- 原型还没过
- 正式 spec 还没写
- 新路径还没真正跑通

所以当前最稳做法是：

### 10.1 `journal_entries.annotations`

- 原型阶段不动
- 如果原型通过，进入正式 spec 时，再把它列为“第一优先级退场候选”
- 真正删除时机应晚于：
  - 新写作路径跑通
  - 展示路径稳定
  - 自动识别 / 搜索 / AI 都确认不受影响

### 10.2 `review_letters.annotations`

- 当前不进入退场范围
- 这是后续独立专题

### 10.3 `threads.current_state_annotations`

- 当前也不进入退场范围
- 同样是后续独立专题

结论：

- 当前文档只能写“退场优先级判断”
- 不能写“现在就删”

---

## 11. 如果原型失败，默认 fallback 什么最优

如果原型失败，不应把失败直接解释成“项目方向全错”。

先分两类：

### 11.1 如果失败原因是交互模型本身不成立

例如：

- 所见即所得样式和自动识别始终互相干扰
- 保存格式导出始终脆弱
- Android / WebView 输入体验无法接受

那默认 fallback 应是：

**继续沿用现有 `plain text + annotations` 正式链路，小步增强，不进入本轮正式迁移。**

### 11.2 如果失败原因是当前实现壳不合适

例如：

- 当前 editor shell 难以区分文字变化和样式变化
- 当前技术实现不适合导出目标保存格式

那 fallback 不是回到大迁移，而是：

**写失败报告，定位问题，再评估更合适的 editor / 实现方式做第二轮隔离原型。**

这与正式链路仍然解耦。

## 12. 当前最推荐路线

### 12.1 核心推荐

当前最推荐路线是：

**先做隔离最小原型，验证“所见即所得写作 + 自动识别稳定共存 + 保存格式可导出”是否成立。**

原型范围严格限定为：

- 只验证 `journal_entries` 写作正文
- 不接 DB
- 不改正式保存链
- 不碰 `review_letters`
- 不碰 `threads`
- 不删任何旧字段

### 12.2 原型通过后才进入下一阶段

若原型通过，下一步应是：

1. 重写正式 spec
2. 再写正式迁移 plan
3. 再按阶段实施

不是原型一过就直接全站开改。

---

## 13. 当前不推荐路线

### 13.1 不推荐路线一：直接把现在的方向文档当正式迁移 plan

原因：

- 原型还没验证
- 关键交互风险未被证明

### 13.2 不推荐路线二：让用户直接编辑 Markdown / tag 源码

原因：

- 与“所见即所得”目标冲突
- 容易干扰自动识别
- 用户体验差

### 13.3 不推荐路线三：现在就强推 `content` 字段正式迁移策略

原因：

- 这属于原型通过后的正式设计问题
- 当前阶段只需记录 A 比 B 更稳

### 13.4 不推荐路线四：现在就写 annotations 删除任务

原因：

- 删除时机依赖原型结果和正式 spec

## 14. 需要用户先拍板的决定项

当前需要先拍板的是：

1. 是否同意本议题回退为“原型验证前的架构决策题”，暂停正式迁移 plan 叙事
2. 是否同意原型目标必须是“所见即所得”，用户不直接看到源码标记
3. 是否同意原型必须验证“样式变化不干扰自动识别”
4. 是否同意原型只碰 `journal_entries` 写作正文
5. 是否同意原型失败后，先写问题报告，再决定是否找其他技术人员 / AI 协助，而不是直接改正式链路

## 15. 原型通过前，下一份 spec / plan 不该越过的边界

在原型通过前，下一份正式 spec / plan 不应越过以下边界：

1. 不写正式 DB schema 迁移任务
2. 不写正式 `content` 字段改造任务
3. 不写 `review_letters` / `threads` 迁移任务
4. 不写 annotations 删除任务
5. 不写全站替换编辑器任务
6. 不把“受限保存格式”直接包装成“已确认正式真源”

---

## 16. 当前结论

我的当前结论是：

- **先做隔离最小原型，是这轮最稳的选择**
- **原型的核心不是验证 Markdown，而是验证所见即所得编辑模型能否稳定导出目标保存格式，并与自动识别共存**
- **在原型通过前，不应进入正式迁移叙事**
- **原型通过后，先重写正式 spec / 迁移 plan，再分阶段实施**
- **这是当前最符合“性能优先、少走弯路、减少返工”的路线**
