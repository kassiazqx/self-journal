# Text Source Direction Plan

> **For reviewer sessions:** This is a decision plan, not an execution-ready implementation plan. Use it to review architecture direction before writing spec/code.

**Goal:** 为 self-journal 确定下一阶段“文本、标注、富文本、段落格式”的唯一真源方向，避免继续长期依赖“纯文本 + offset 套样式”的分裂模型。

**Architecture:** 当前项目已经有 `RichTextEditor`（Lexical）编辑态，与 `AnnotatedText` 只读态两条链。下一阶段需要在“直接把 Lexical JSON 作为唯一真源”与“自定义文档模型 JSON 作为唯一真源”之间做取舍，并明确对搜索、AI 提取、导出、APK 的影响。建议优先采用“Lexical JSON 主存 + app-owned adapter/repository + 派生纯文本”的分阶段路线，而不是继续纯文本主存，也不是现在立刻全量自研文档模型。

**Tech Stack:** React, Lexical, existing `RichTextEditor`, existing `AnnotatedText`, Supabase, current annotation system

---

## 1. 当前问题

当前代码里，文本相关事实实际上分散在三层：

1. `RichTextEditor` 里的编辑器状态
2. `journal_entries.content` / 各类字符串字段里的纯文本
3. `annotations` 里基于字符位置的标注数据

这会导致几个长期问题：

- 输入态和展示态不是同一个文档模型
- 段落/换行规则在不同页面无法天然统一
- 标注与文字不是一体结构，而是“后贴上去”
- 一旦未来继续做更丰富的文本结构，offset 更脆弱

用户已经明确的新目标：

- 新内容开始，输入与输出尽量看到同样的结构
- 段落规则统一
- 标注/富文本和文字本身尽量在一个模型里
- 不再把“只读页按 offset 套样式”当终局方案

---

## 2. “被 Lexical 结构绑死”是什么意思

不是说现有导出/搜索今天就会坏。

意思是：如果数据库主存直接是“未经抽象的裸 Lexical JSON”，那未来很多能力都会被它的内部节点结构牵着走。

典型表现：

1. 搜索
   - 你真正要搜索的是“用户最终看到的文字”
   - 但裸 Lexical JSON 里可能有段落节点、装饰节点、标注节点、换行节点等结构细节
   - 如果以后每次搜索都要先理解 Lexical 结构，业务层就被编辑器模型绑住了

2. AI 清洗 / AI 提取
   - AI 通常需要稳定、干净、可预测的纯文本或轻结构文本
   - 如果业务链直接读裸 Lexical JSON，就必须写很多“把编辑器节点还原为 AI 可读文本”的逻辑
   - 一旦编辑器节点形态变了，AI 清洗链也要跟着改

3. 导出
   - 导出 Markdown / HTML / TXT / PDF 时，真正需要的是“文档语义”
   - 如果直接从裸 Lexical 节点导，导出层也会依赖编辑器私有结构
   - 将来换编辑器时，导出链几乎要一起重写

4. 跨平台
   - Web 现在用 Lexical 很合理
   - 但 APK 阶段如果编辑器能力、插件能力、性能策略变化，业务层最好不要直接依赖 Lexical 的内部 JSON 细节

所以“被绑死”更准确的人话是：

- 不是功能马上坏
- 而是以后每加一个能力，都得先和 Lexical 内部结构打交道
- 编辑器从“输入工具”变成了“数据库格式定义者”

---

## 3. 现有导出 / 搜索 / AI 会不会被影响

### 3.1 搜索

现有搜索主要仍围绕纯文本字段工作。

如果转向“富文本/文档状态做唯一真源”，搜索不会消失，但需要明确新策略：

- DB 主存不再只靠 `content`
- 同时维护一个派生的 `plain_text` / `search_text`
- 搜索继续对派生文本做，而不是直接对文档 JSON 做复杂查询

结论：

- 会改数据流
- 但不会让搜索能力变差
- 正确做法是“文档真源 + 派生搜索文本”，不是“搜索直接啃文档 JSON”

### 3.2 AI 提取 / AI 清洗

现有 AI 提取链也是偏纯文本思路。

未来如果主存改成文档状态，建议统一提供一层：

- `buildEntryPlainTextFromDocument(doc)`
- `buildEntryAiTextFromDocument(doc)`

这样 AI 链拿到的仍是稳定文本，不直接读编辑器 JSON。

结论：

- 会增加一层转换
- 但这是好事，因为能把 AI 与编辑器结构隔开

### 3.3 导出

如果以后做完整导出，文档真源反而更有利。

因为可以稳定派生：

- TXT：纯文本
- Markdown：段落/强调/高亮等映射
- HTML：结构化输出

结论：

- 不会让导出更差
- 反而比“纯文本 + offset”更适合长期导出

## 4. 方案 A：Lexical JSON 作为唯一真源

### 4.1 方案定义

- DB 主存：Lexical EditorState JSON
- `RichTextEditor` 直接读写这份 JSON
- 只读页不再靠 `content + annotations` 拼，而是从这份 JSON 渲染
- 搜索 / AI / 导出使用派生文本，不直接以纯文本为主存
- 业务层通过 repository / adapter 访问，不让页面直接依赖 Lexical JSON 细节

### 4.2 优点

1. 开发速度最快
   - 现有编辑器已经是 Lexical
   - 不需要今天重新造一套完整文档引擎

2. 新 bug 风险相对更低
   - 复用现成编辑器状态模型
   - 少写一层自定义编辑行为

3. 更容易尽快达成“输入输出尽量一致”
   - 编辑态与展示态可以围绕同一份文档状态收口

4. 最适合本项目当前阶段
   - 你现在要解决的是统一文本规则
   - 不是立刻做 Notion 级文档内核

### 4.3 缺点

1. 长期仍受 Lexical 结构约束
2. 未来换编辑器成本高
3. 导出/AI/搜索都必须经过“Lexical -> app plain text/HTML”适配层
4. 若直接把裸 Lexical JSON 散到业务代码，会形成新的技术债

### 4.4 适用前提

这个方案只有在以下条件成立时才推荐：

- 业务层不直接到处读写裸 Lexical JSON
- 必须建立 `documentRepository` / `documentAdapter`
- 必须同时维护派生纯文本
- 必须提前定义“允许哪些节点类型”，不把编辑器默认能力无限放开

---

## 5. 方案 B：自定义文档模型 JSON 作为唯一真源

### 5.1 方案定义

- DB 主存：项目自定义 `doc_v1` JSON
- 例如：
  - `doc`
  - `paragraph`
  - `text`
  - `marks`
  - `image`
  - `mention`
- Lexical 只作为编辑器 UI
- 编辑时：`doc_v1 -> Lexical`
- 保存时：`Lexical -> doc_v1`
- 展示页直接渲染 `doc_v1`

### 5.2 优点

1. 控制权最高
   - 文档模型属于项目自己，不属于某个编辑器

2. 长期最稳定
   - 换编辑器、上 APK、做导出、做 AI 清洗，都更可控

3. 最符合“文字与标注一体化”的终局方向
   - 文档天然可表达段落、文字节点、样式、图片、mention 等

4. 业务层语义更清晰
   - 不必把编辑器内部节点当业务模型

### 5.3 缺点

1. 现在开发量最大
2. 需要自己维护双向转换
   - `doc_v1 -> Lexical`
   - `Lexical -> doc_v1`
3. 最容易引入新 bug
   - 保存错
   - 渲染错
   - 转换丢样式
   - 图片/mention/标注边界错
4. 对当前项目节奏更重
   - 这已经不是“排版统一”
   - 而是“新文档模型工程”

### 5.4 适用前提

只有在以下前提都愿意接受时才建议现在直接做：

- 接受开发周期显著变长
- 接受首轮 bug 风险更高
- 接受需要先做大量转换和迁移设计
- 接受这轮不只是 UI/文本规则，而是底层架构专项

---

## 6. 两个方案的直接对比

| 维度 | 方案 A：Lexical JSON 真源 | 方案 B：自定义 doc JSON 真源 |
|---|---|---|
| 当前开发速度 | 快 | 慢 |
| 当前 bug 风险 | 中 | 高 |
| 长期控制权 | 中 | 高 |
| 换编辑器成本 | 高 | 低 |
| APK 可迁移性 | 中 | 高 |
| 达成“尽快统一输入输出” | 强 | 中 |
| 达成“终局一体化模型” | 中 | 强 |
| 对团队当前复杂度压力 | 低到中 | 高 |

## 7. 我的建议

### 7.1 推荐路线

推荐采用：

**阶段路线，而不是二选一硬切。**

具体是：

### Phase 1

先上：

**Lexical JSON 主存 + app-owned repository/adapter + 派生纯文本**

目标：

- 先把唯一真源从“纯文本 + offset”切走
- 尽快统一输入/展示/段落规则
- 不在这一轮立刻自研完整 doc model

### Phase 2

等文本统一链稳定后，再评估是否迁到：

**自定义 `doc_v1`**

前提信号：

- 业务层已经明显受 Lexical 节点限制
- 导出 / AI / APK 适配频繁要读内部结构
- 新内容元素（图片、附件、mention、callout、引用等）持续增多

### 7.2 为什么不直接建议现在上方案 B

因为你当前最明确的痛点是：

- 输入输出不统一
- 段落规则不统一
- 文字和标注关系太散

这几个问题，方案 A 已经能解决大头。

如果现在直接做方案 B，会把专项规模扩大成：

- 新文档模型设计
- 双向转换
- 迁移策略
- 编辑态和只读态全重接
- 测试矩阵大幅扩张

这不是不能做，而是当前收益/风险比不一定最好。

### 7.3 什么时候应该直接上方案 B

如果下面这些条件你都明确接受，才建议跳过 A 直接做 B：

- 允许这轮做成一个明显更大的底层工程
- 接受周期更长
- 接受第一轮转换 bug 明显更多
- 接受先花更多时间在模型，而不是先快速交付统一文本体验

## 8. 建议的下一步文档顺序

如果采纳推荐路线，下一步不要直接写代码，顺序应是：

1. 写新 spec
   - 明确段落规则
   - 明确唯一真源
   - 明确派生纯文本策略
   - 明确旧数据迁移/降级策略

2. 再写实施 plan
   - 数据模型任务
   - repository / adapter 任务
   - 编辑页接入任务
   - 展示页接入任务
   - 搜索 / AI 文本派生任务
   - 验证矩阵任务

3. 再进代码 session

## 9. 给审查者的重点问题

交给 Claude/架构审查时，重点请看：

1. 是否同意“纯文本 + offset”不再作为终局方向
2. 是否同意“先 Lexical JSON 主存，再保留迁移到 doc_v1 的接口”这个阶段路线
3. 是否认为当前项目已经值得直接跳过 Phase 1，立刻做自定义 `doc_v1`
4. 是否有更好的 repository / adapter 边界建议
5. 搜索 / AI / 导出是否应该统一经过同一个 plain-text builder

---

## 10. 当前结论

我的结论是：

- **唯一真源：必须要**
- **继续纯文本主存：不建议**
- **现在立刻自定义 doc model：能做，但偏重**
- **最稳建议：先 Lexical JSON 真源，但严格包 adapter，不让业务层直接绑死**

这条路线能最快解决当前最痛的问题，同时不给以后迁移自定义文档模型堵死路。
