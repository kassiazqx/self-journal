# 架构前瞻讨论（第一版草稿）

> 这不是最终定稿，而是一份先把大方向、风险点、未来扩展口记下来的工作文档。后面你给我新的 checklist 和思维框架后，我再继续补强。

## 1. 当前项目的真实阶段

这个项目现在仍然处在**快速试验 + 频繁调整产品方向**的阶段。

相关草案：
- 本地 app 开发 workflow：`docs/design/local-app-dev-workflow.md`

目前用 Supabase 云端存储，最大的价值不是“最终方案”，而是：
- 方便在电脑上快速打开本地网页测试
- 随时保留测试数据，不怕刷新丢失
- 登录、多端、AI 记忆这些能力都能先跑起来
- 功能验证时，不需要先解决本地数据库、同步、备份这些更重的问题

所以，**当前架构更像是“验证产品形态”的架构，不是“最终发布形态”的架构。**

这点非常重要，因为后面很多设计都要区分：
- 什么是“现在就必须做对的基础接口”
- 什么是“现在先不做，但必须留升级口”

---

## 2. 当前最该防止的问题

不是“功能做不出来”，而是下面这三类问题：

### 2.1 业务逻辑散落在 UI 组件里

现在不少页面组件同时负责：
- 渲染 UI
- 处理交互状态
- 直接调 Supabase
- 做数据转换
- 做副作用流程控制

短期开发会很快，但后面一旦：
- 想改 UI
- 想改存储层
- 想加本地优先策略
- 想把某段流程复用到别的页面

就会越来越难维护。

### 2.2 默认规则硬编码在多个文件里

例如模板配置、关键词映射、标签分组、提示词字段约定，很多地方都有“同一份业务知识在多个文件重复出现”的迹象。

这种结构最大的问题不是“看起来乱”，而是：
- 以后改一个概念，要同时改多个文件
- 很容易漏改
- UI 改动和业务改动容易缠在一起

### 2.3 缺少“未来替换底层实现但不动上层调用”的接口

如果以后你要：
- 把 Supabase 换成本地数据库
- 把 Web Speech 换成原生语音能力
- 把 localStorage 换成手机安全存储
- 把 AI Key 本地存储换成后端代理

理想状态应该是：**调用方几乎不动，只替换底层实现。**

现在有些模块已经做到这点了，比如 `aiClient.js`、`memory.js`、`useSpeechRecognition.js`，但还不够全面。

---

## 3. 之后应该往什么样的结构收敛

目标不是一开始就过度工程化，而是逐步收敛到下面这种分层：

### 3.1 UI 层

职责：
- 展示界面
- 接收用户点击/输入
- 调用业务层接口
- 管理局部交互状态

不应该承担：
- 直接写数据库
- 拼装复杂业务流程
- 管理跨页面的业务规则

### 3.2 业务服务层

职责：
- 处理日记保存、对话保存、字段提取、用户选项更新等业务动作
- 决定先做什么、后做什么
- 控制副作用顺序

建议逐步形成这些模块：
- `journalService.js`
- `conversationService.js`
- `userOptions.js`
- `userSettings.js`

### 3.3 检测/规则层

职责：
- 关键词检测
- 事件识别
- 内容复杂度分析
- 问题卡片生成

这层的关键要求是：**输入输出稳定，内部实现可替换。**

例如：
- 今天是关键词匹配
- 以后可以换成本地模型
- 再以后也可以换成 AI

但调用它的页面不应该跟着重写。

### 3.4 存储适配层

这是现在还没有完全成型、但未来很关键的一层。

理想上，后面要逐步做到：
- 现在：Supabase 为主
- 未来：本地存储 / 本地数据库也能跑
- 再未来：本地优先 + 云端同步

也就是说，上层最好不要直接依赖“Supabase 这个具体名字”，而是依赖“保存日记”“查询选项”“更新记忆”这些动作。

---

## 4. 为什么之后 UI 大改前，必须先补这些基础接口

你后面明确会把 UI 全部改掉，变得更漂亮。

如果现在不先把业务和 UI 慢慢拆开，那么之后改 UI 时就会出现：
- 改一个输入框样式，顺手碰到数据库逻辑
- 改一个页面布局，顺手碰到流程跳转状态
- 改一个按钮组件，顺手碰到业务判断

这样 UI 改造会非常痛苦。

所以从可维护性的角度，**现在最值钱的不是“多做几个功能”，而是把业务逻辑慢慢从页面组件里挪出来。**

这件事不是为了代码好看，而是为了给未来的大 UI 重做腾空间。

---

## 5. 关于 Supabase：它现在是“验证期基础设施”，不一定是最终形态

你提到一个很重要的判断：

> 现在用 Supabase 云端记录，主要是为了测试方便；如果手机端之后也能同样方便，本地优先也未必不行。

这个判断是成立的，而且应该被单独当成一个架构讨论项，而不是默认把 Supabase 当成永远的终局。

### 5.1 当前继续用 Supabase 的价值

在当前阶段，Supabase 仍然很有价值，因为它天然提供了：
- 登录系统
- 云端数据保存
- 跨设备同步
- 快速查看线上真实数据
- 几乎零后端维护成本

这对“产品形态还在变”的阶段非常有帮助。

### 5.2 但它不一定是最终答案

如果未来你的主要使用场景变成：
- 手机上的个人私密日记
- 更多离线使用
- 更重视本地响应速度
- 不想长期依赖外部云服务

那么“本地优先”甚至“纯本地存储”都可能成为更合理的路线。

### 5.3 所以现在真正该做的，不是争论最终用哪种，而是避免被绑死

也就是说，现在更重要的是：
- 不让页面组件直接写死 Supabase 调用
- 不让业务逻辑和 Supabase 表结构强耦合
- 让“保存日记 / 查询历史 / 更新记忆”变成稳定动作接口

这样以后才可能平滑切换成：
- 方案 A：继续 Supabase 云端为主
- 方案 B：本地优先 + 后台同步
- 方案 C：纯本地存储（单机版）

### 5.4 未来可能的三条路线

#### 路线 1：继续云端优先
- 优点：多端同步简单，网页登录和调试方便
- 缺点：依赖外部服务，离线体验一般，隐私感知较弱

#### 路线 2：本地优先 + 云端同步
- 优点：本地体验好，离线可写，仍可多端同步
- 缺点：实现最复杂，需要同步策略、冲突处理、恢复机制

#### 路线 3：纯本地优先
- 优点：隐私强、响应快、结构简单、无服务依赖
- 缺点：跨设备同步差，备份与迁移要另想办法

### 5.5 当前阶段的最佳策略

当前不应该直接切换到本地方案，但应该开始按“以后可能切换”来设计接口。

所以短期建议是：
- **产品运行继续基于 Supabase**
- **代码结构开始去 Supabase 直连化**
- **把存储层逐步包成 service / repository 风格接口**

这样以后不管你选云端、本地，还是混合路线，都还有转向空间。

## 6. 接下来真正值得提前预留的“插座”

下面这些不是现在全做，而是现在就要在结构上留位置：

### 6.1 用户设置中心
未来设置页不只是 API Key，而应该逐步承接：
- 标签管理
- 关键词映射管理
- 事件/人物别名管理
- 提醒设置
- 主题设置
- 数据导出 / 清理 / 恢复

### 6.2 原子 UI 组件层
未来要整体大改 UI，就应该逐步把按钮、输入框、卡片、弹层、标签这些抽成统一组件。

### 6.3 存储层替换能力
未来如果切换到本地数据库、Capacitor Preferences、SQLite、同步层，页面层不应大改。

### 6.4 规则可配置化
现在关键词和问题库多为硬编码，未来如果你希望自己在产品内可编辑，就要让默认规则和用户自定义覆盖规则能合并。

### 6.5 平台适配层
后面打包 Android / iOS 时，键盘、返回键、通知、语音、权限这些都需要单独适配层，不应散落在页面里。
