# 本地 App 开发 Workflow（草案）

> 用途：以后开始做“本地数据优先”的 Android / iOS app 时，快速看一眼，提醒自己怎么开发、怎么测试、哪些地方先别想太重。
>
> 状态：草案，不是最终技术方案。

---

## 1. 一句话原则

- 只维护 **一套产品逻辑 / 一套页面代码**
- 可以有 **多个运行环境**
  - 浏览器（开发快）
  - Android 模拟器（接近 app）
  - 真机 APK / iOS（最终验收）
- “继续用 web 开发” 不等于 “继续依赖云端数据”

---

## 2. 先记住最重要的区分

### 2.1 运行环境

- 浏览器
- Android 模拟器
- 真机

这是“页面跑在哪”。

### 2.2 数据存储

- 小设置：本地 key-value
- 核心业务数据：本地数据库
- 云端同步：以后可选，不是默认前提

这是“数据放在哪”。

这两件事不要绑死理解。

---

## 3. 当前倾向

如果产品进入“本地 app 阶段”，默认倾向是：

- `API key` / `letter_prefs` / 草稿：本地存储
- `journal_entries` / `conversations` / `review_letters` 等核心数据：本地数据库
- 云端同步：以后需要多设备时再单独设计，不在第一版本地 app 强行并行

---

## 4. 开发时怎么分工

### 4.1 浏览器适合做什么

- 快速调 UI
- 普通状态逻辑
- 文案 / 布局 / 交互节奏
- 不依赖手机权限的页面流程

浏览器阶段可先用：

- `localStorage` / `Preferences` 思维调小设置
- `IndexedDB` 调本地数据流

### 4.2 模拟器适合做什么

- 键盘避让
- 输入法
- 返回键
- 滚动手感
- 图片选择 / 文件 / 权限
- 更接近 app 的页面切换体验

### 4.3 真机必须测什么

- 最终手感
- 键盘 / 软键盘高度
- 图片与文件链路
- 性能卡顿
- 权限弹窗
- 真正的保存 / 恢复 / 重开 app

---

## 5. 推荐工作流

### 日常开发

1. 先在浏览器里改页面和业务逻辑
2. 涉及移动端行为时切到模拟器复看
3. 一个功能收尾前，用真机走一遍主流程

### 涉及本地存储的功能

1. 先把“调用接口”定好
2. 浏览器里先跑本地版逻辑
3. 再把底层实现替换到 app 本地存储
4. 真机验证“刷新 / 关闭重开 / 恢复”

### 不建议的做法

- 页面里直接绑死 Supabase
- 页面里直接绑死 localStorage / IndexedDB / SQLite
- 一开始就做“本地 + 云端双真源”

---

## 6. 关于 IndexedDB 和 SQLite

这不是“两套系统”，更像“两个本地环境的底层实现”。

- 浏览器本地调试：更可能用 `IndexedDB`
- App 正式版：更可能用 `SQLite` / 原生本地存储

上层最好只看到统一接口，例如：

- `getEntry(id)`
- `saveEntry(entry)`
- `listEntries()`
- `saveLetterPrefs(userId, prefs)`

以后如果接口不变，只替换底层 adapter，页面层就不用重写。

---

## 7. 什么时候才考虑云端同步

只有在以下问题变成真实需求时，再单独开一批设计：

- 一个账号多设备同步
- 换机后自动恢复
- 数据备份上云
- 团队协作 / 网页和 app 共用同一份正式数据

在那之前，不要为了“以后可能会用”提前做复杂双源。

---

## 8. 后续真正进入本地 app 阶段时，要先确认的 5 个问题

1. 哪些数据是“小设置”，哪些是“核心业务数据”？
2. 核心业务数据第一版是否完全脱离 Supabase？
3. 浏览器开发阶段是否需要一份可导入的本地测试数据？
4. 哪些功能必须模拟器测，哪些必须真机测？
5. 数据导出是否要覆盖设置、草稿、正式记录三类内容？

---

## 9. 暂时结论

- 可以继续用 web 作为开发工具
- 不必因此继续依赖云端
- 不必维护“web 产品”和“app 产品”两套系统
- 最终目标是：一套代码，多运行环境，存储层可替换
