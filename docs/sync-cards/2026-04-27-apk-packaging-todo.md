## 背景

当前记录删除分成两类数据：

- `journal_entries` 里的文字/字段
- `imageStorage` 管的图片文件

现在两者不是统一删除流：

1. 单条删除：
   - `RecordsPage.handleDelete()` 先调 `deleteEntry()`
   - 但不检查返回结果，就继续删图片、移除本地列表、关闭确认框
2. 批量删除：
   - 先删图片
   - 再删 DB
3. `deleteImage()` 失败只 `console.error`，不会抛异常

所以会出现两种不一致：

- DB 没删掉，但界面先当成删掉了
- 记录还在，但图片先没了

目前用户已接受：这个问题真实存在，但暂时可见、可重试，不作为本轮阻塞项。

---

## 当前目标

这件事先不马上改代码，但要保留清晰口径，方便后续在以下时机统一处理：

- 专门收口删除语义时
- 开始做 APK / 本地存储方案时
- 需要把“文字 + 图片”真正当成一条完整记录管理时

补充口径：

- reviewer 提到的“单删和批删共用同一个 helper / service”不单独立项
- 如果以后要修，就和“删除成功判断 + 删除顺序”一起修
- 不做只抽结构、不改语义的空重构

## 这次先不改的原因

- 当前主线不是删除系统重构
- 现在的风险更接近“删不干净”或“前端假成功”，不是完全无痕的数据黑洞
- 真正理想解法不是在 `RecordsPage` 里继续补 if/else，而是把删除责任往统一数据层收

## 后续推荐方案

### 方案 1：轻量修正版（未来若要先补，优先做这个）

目标：先把最危险的不一致收掉，但不改大架构。

建议规则：

- 先删 DB
- 只有 DB 成功，才更新 UI、关闭确认框、退出多选
- 图片清理放到 DB 成功后做 best-effort
- 单删和批删共用同一个删除 helper / service

效果：

- 不会再出现“DB 没删掉，但 UI 已经假装成功”
- 若图片删失败，只留下孤儿图片，不影响用户看到的记录正确性

代价：

- 仍不是严格原子删除
- 仍可能残留孤儿图片

### 方案 2：长期理想版（更适合 APK / 本地存储阶段一起做）

目标：把“删一条记录”收成一个统一动作，而不是页面自己拼步骤。

方向：

- 由统一 service / repository 负责整条记录删除
- 上层页面只发一个“删除这条记录”的请求
- service 内部决定文字、图片、派生数据的删除顺序和回滚策略

如果未来打包 APK 并转向本地存储：

- 物理上，文字和图片未必真的存在同一个文件里
- 但逻辑上可以收口成同一个系统入口
- 这样页面层不用关心“先删表还是先删文件”

---

## 为什么这和 APK 本地存储有关

现在图片已经走 `imageStorage.js` 抽象层，这本来就是为未来存储迁移留的接缝。

后续如果做 APK：

- 图片可能从 Supabase Storage 切到本地文件目录
- 文本/字段可能仍在本地数据库或另一层持久化里
- 这时更需要一个统一删除流，否则 Web 时代的分散逻辑会继续带到 App 里

一句话：

现在先记住的不是“以后把图片放哪”，而是“以后删除必须由统一数据层负责，不让页面自己拼删除顺序”。

## 追加提示：默认用户数据初始化在 APK / 本地优先阶段的收口方向

如果后续开始做 Capacitor APK + 本地存储 / 离线写日记，默认用户数据初始化也要一起升级，但不是把这次 Web 方案全部推翻。

### 当前 Web 阶段先记住

- 默认 `content_category / core_need / user_contacts` 已收口为代码单一真源
- Web 阶段用 `localStorage marker` 只是过渡方案，不是长期最终真相源
- 当前目标是“别偷偷回填、别重复插、别分散 seed”

### APK / 本地优先阶段要升级的点

1. **去掉 localStorage marker，迁到正式持久层**
   - 不再把“是否已初始化”放在 Web localStorage
   - 改放到本地数据库字段/初始化状态表里
   - 必要时再和云端账号状态对齐

2. **初始化落点前移到本地数据库**
   - 现在主要围绕 Supabase + Web localStorage
   - 以后应先把默认分类 / 联系人 / core_needs 写入本地数据库（如 SQLite）
   - 这样离线首开也能完整可用

3. **App 启动先读本地，再考虑云端**
   - 页面层继续只读统一 service / repository
   - 不让页面自己判断“现在该从 Supabase 还是本地拿默认数据”

4. **同步语义要和默认数据一起定义**
   - 新设备首次同步时，不能因为云端 / 本地都为空就重复塞两份默认值
   - 要提前写死：默认数据到底是“账号级初始化一次”还是“设备级初始化一次”

5. **Settings 页局部文案可以复用**
   - `正在准备联系人词库...` 这种局部提示在 APK 阶段仍可保留
   - 但那时含义会变成“正在等本地数据库初始化/恢复”，不再是等 Web bootstrap

### 和这次批次的关系

补充结论：默认用户数据这次先完成“Web 阶段单一真源 + 非偷偷回填 + 并发重复保护”；等进入 APK / 本地优先批次，再把初始化状态从 `localStorage` 迁到本地数据库 / 正式持久层。

## 追加提示：APK 真正开工前后，还要补哪些收口

这段不是本轮立刻做，只是给以后打包 APK 时当 checklist。

### APK 开工前先定 5 件事

1. **账号路线先定**
   - 要不要继续保留 Supabase Auth
   - 登录主方式用邮箱验证码、手机号验证码，还是先不上账号体系

2. **本地持久层先定**
   - 简单偏好类：`localStorage` → `Capacitor Preferences`
   - 结构化数据：`Supabase` 直读写 → 本地数据库/正式持久层优先

3. **图片/附件存储先定**
   - Web 过渡逻辑不能直接当 APK 终局
   - 进入 APK 后要按 `mediaItems[] + 本地文件目录` 方向收口

4. **登录跳转和会话恢复先定**
   - 若继续用 Supabase Auth，要补 deep link / app scheme / 回到 App 后续登逻辑

5. **备份恢复语义先定**
   - 这 App 最终是本地优先、云同步、还是单机为主
   - 不先定，后面删除/同步/迁移都会反复摇摆

### APK 打包后第一批建议做什么

1. 跑通 `Capacitor Preferences`，把设置类 `localStorage` 收口
2. 给 Auth 补 App deep link / session restore
3. 确认本地数据库方案，别再让页面直接依赖 Web Storage 心智
4. 把图片链往 `mediaItems[] + 本地文件` 收
5. 做一轮真机验证：登录、退出、断网、重开、删除、恢复

### 账号/登录方案 A/B/C

#### 方案 A：继续 `Supabase Auth + 邮箱 OTP`

- **最适合现在**
- 登录方式改成 6 位邮箱验证码（OTP）
- 邮件标题/文案/发件邮箱可改，但正式环境通常要接自定义 SMTP
- 优点：改动最小、成本最低、先上 APK 最快
- 缺点：国内邮箱到达率/体验一般，仍依赖邮箱

#### 方案 B：继续 `Supabase Auth + 手机验证码`

- 仍保留 Supabase Auth，只把登录入口换成手机号 OTP
- 通常要接短信供应商（如腾讯云/阿里云）+ Supabase SMS Hook
- 优点：更像国内 App，用户理解成本低
- 缺点：接入和成本都高于邮箱 OTP，要处理短信费用/风控/地区限制

#### 方案 C：APK 走本地优先，账号体系后置或弱化

- App 主数据先放本地数据库，账号只做“可选备份/同步”
- 首次可先游客/本机使用，后续再绑定邮箱或手机号
- 优点：最符合“日记工具、本地优先、弱联网可用”
- 缺点：产品和数据迁移语义更复杂，要提前想清楚换机/恢复/多端同步

### 当前推荐口径

- **短期最优：方案 A**
  - 先保留 `Supabase Auth`
  - Web 和 APK 都先走邮箱 OTP
  - 真到国内转化率或到达率不够，再升级方案 B

- **长期最优：偏方案 C**
  - 数据层走本地优先
  - 账号层降级成“同步/恢复能力”，不是 app 核心前提
  - 若后面需要更强国内化登录体验，再在 C 的基础上叠加 B
