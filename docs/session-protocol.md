# Multi-Session 协作规范 | session-protocol.md

> 本文档定义三个 Claude session 的行为规范，解决并发开发时的信息偏差问题。
>
> **核心原则：** 不靠人记忆，靠结构防护。

---

## 概述：三个 Session 的分工

| Session | 职责 | 主维护文档 |
|---|---|---|
| 产品 session | 功能方向、用户体验、心理专业判断 | docs/superpowers/specs/ + plans/ |
| 代码 session | 实现功能、写代码、跑 build | src/ 代码 |
| 架构 session | 代码质量、安全、debug、可维护性 | docs/arch-context.md §4 §5 |

**文档是 session 间唯一可靠的通信方式。**

---

## 第一层：产品 Session 规范

### 1.1 何时必须输出同步卡

以下任何一种变更发生，产品 session 在该次对话结束前必须输出一张同步卡：

- 数据表结构变了（新增字段/表、字段类型变化）
- 数据流向变了（谁写哪张表、读取顺序变了）
- 组件/模块边界变了（某个功能从一个模块移到另一个）
- 功能被取消或被替代（防止代码 session 继续实现已废弃的功能）
- 某个设计决策被推翻（之前定好的"不要做 X"改成了"要做 X"）

**不需要同步卡的变更：**
- 文案调整
- 颜色/样式微调
- 新增一个独立功能（不影响已有代码路径）

### 1.2 同步卡模板

```
📋 同步卡 | {YYYY-MM-DD}
───────────────────────────────
本次变更：{一句话描述变更内容}
涉及 spec：{文件名} §{章节号}（如有）
影响代码文件：{具体文件路径或模块名}
影响数据库：{字段/表名变化，没有就写"无"}
───────────────────────────────
代码 session 需要做：
  1. 读 {spec 文件} §{章节}
  2. {具体要注意什么，一句话}
  3. {如果需要额外操作，列出来}
───────────────────────────────
请把这张卡发给代码 session，等它输出确认后再继续
```

### 1.3 示例同步卡

```
📋 同步卡 | 2026-04-11
───────────────────────────────
本次变更：conversations 表的保存从 INSERT 改为 UPSERT，UNIQUE(entry_id, context_type)
涉及 spec：2026-04-09-self-journal-redesign-design.md §4.1
影响代码文件：src/components/AwarenessFlow.jsx 的 upsertConversation 函数
影响数据库：conversations 表新增 UNIQUE 约束
───────────────────────────────
代码 session 需要做：
  1. 读 spec §4.1 的 UPSERT 规则说明
  2. 确认 upsertConversation() 用的是 upsert() 而不是 insert()
  3. 确认传入的是完整 messages 数组而不是增量
───────────────────────────────
请把这张卡发给代码 session，等它输出确认后再继续
```

## 第二层：代码 Session 规范

### 2.1 每个 Plan 的 Task 0（必须执行）

每次代码 session 开始执行一个新的 plan 任务时，第一步必须是 Task 0。

**Task 0 模板（放在每个 plan 文件的开头）：**

```markdown
## Task 0：上下文同步（必须完成才能继续）

- [ ] 读 docs/arch-context.md §2（已确认架构决策）
- [ ] 读本任务对应的 spec 文件相关章节（见下方"前置阅读"）
- [ ] 输出确认句（见格式要求）
- [ ] 如发现不一致：列出偏差，停下来等用户确认，不自行修复

**确认句格式：**
✅ 上下文已同步：
- 当前主数据路径：[简述]
- 本次任务涉及：[文件/模块名]
- 与 spec 对比：[一致 / 有偏差（列出偏差）]
```

### 2.2 发现偏差时的处理流程

```
代码 session 发现"代码现状"与"spec/arch-context 描述"不一致
  ↓
立刻停下来，输出偏差报告
  ↓
格式：
⚠️ 发现偏差：
- spec 说：[spec 里的描述]
- 代码现状：[实际代码里的情况]
- 我的判断：[哪个是当前有效版本？不确定]
- 我的建议：[保留哪个 / 如何修复]
  ↓
等用户确认后，按确认结果继续
  ↓
不自行修复，不根据"感觉对"的方向推进
```

### 2.3 接到同步卡后的处理

当用户把产品 session 的同步卡发过来时：

1. **立刻暂停当前任务**
2. 读同步卡里指定的 spec 章节
3. 对照已有代码，确认影响范围
4. 输出确认：
   ```
   ✅ 同步卡已读取
   影响确认：[列出哪些文件/逻辑需要调整]
   当前进度：[正在做什么，是否需要先回滚/调整]
   建议：[继续当前任务 / 先处理同步卡变更]
   ```
5. 等用户决定后继续

## 第三层：架构 Session 规范

### 3.1 冷启动步骤（每次启动必须执行）

被唤醒时，**在回答任何问题之前**，按顺序执行：

```
1. 读 CLAUDE.md（项目全貌和工作规范）
2. 读 docs/arch-context.md（当前架构全貌）
3. 读 docs/superpowers/specs/ 下最新的 spec 文件
4. 读 docs/superpowers/plans/ 下最新的 plan 文件
5. 运行 git log --oneline -10（了解最近变更）
6. 扫描 src/ 目录结构（了解当前代码状态）

完成后，输出：
✅ 冷启动完成
当前架构状态摘要：[2-3句话描述现在的状态]
与上次对比（如果有）：[有无重大变化]
我对当前架构的理解：[确认关键决策点理解正确]
然后再处理你的问题。
```

### 3.2 架构审查输出格式

```
🔍 架构审查
───────────────────────────────
审查范围：[文件/模块/功能]
发现问题：
  - [问题1]：[具体在哪里，为什么是问题]
  - [问题2]：...

风险等级：
  A级（需立即修复）：...
  B级（下次迭代修复）：...
  C级（记录到 §4，暂不处理）：...

最小修复建议：
  - [修复1]：[改哪里，怎么改，影响范围]
  
不建议修复的（原因）：
  - [某问题]：当前阶段代价大于收益，记录风险即可
```

### 3.3 更新 arch-context.md 的触发条件

架构 session 必须更新 `docs/arch-context.md` 的情况：

- 发现新的架构风险 → 追加到 §4
- 确认新的扩展约束 → 追加到 §5
- 完成修复后 → 在 §4 对应条目标记"已修复"
- 发现文档与代码不一致 → 更新 §3（代码真实结构）
- 每次工作结束 → 在 §6 追加一行同步摘要

## 4. 分支与上线纪律

- 所有开发和文档改动先落 `dev`
- 禁止直接在 `main` 上提交任何改动
- 当前阶段允许在 `dev` 连续 commit；等用户确认“没问题”后，再执行 `main <- dev` 合并
- `main` 只承担发布入口职责，不承担日常开发
- 若 `dev` 与 `origin/dev` 分叉，先同步远端（rebase 或 merge），再继续开发或上线

## 用户操作指南

### 场景一：产品 session 产生了架构调整

```
1. 产品 session 输出同步卡
2. 你把同步卡复制给代码 session
3. 代码 session 暂停当前任务，确认影响
4. 你决定：先处理同步卡变更 / 先完成当前任务再处理
5. 代码 session 按决定继续
```

### 场景二：唤醒架构 session

```
1. 打开新的 Claude Code 对话
2. 发送启动 prompt（见下方模板）
3. 架构 session 自动加载上下文
4. 提出你的问题
```

**架构 session 启动 prompt 模板：**

```
你是这个项目的首席架构师和代码安全专家，极度严谨。

请先执行冷启动步骤（见 docs/session-protocol.md §3.1），
完成后告诉我你对当前架构状态的理解摘要，然后再处理我的问题。

我的问题是：[你的具体问题]
```

### 场景三：代码 session 需要校验当前理解

```
发给代码 session：

在继续写代码之前，请做一个上下文自检：
1. 读 docs/arch-context.md
2. 读最新的 spec/plan 文档
3. 对照现有代码，告诉我：你理解的当前架构和文档描述有没有不一致的地方？
4. 列出来，不要自己修，等我确认
```

## 文档更新规则

### 什么变了，谁来更新

| 变更类型 | 更新哪里 | 谁来更新 |
|---|---|---|
| 功能目标/原则变了 | spec 文档 + arch-context §1 §2 | 产品 session |
| 设计决策变了 | spec 文档 + arch-context §2 | 产品 session |
| 代码结构变了 | arch-context §3 | 代码 session |
| 发现架构风险 | arch-context §4 | 架构 session |
| 发现扩展约束 | arch-context §5 | 架构 session |
| 任何重大变更 | arch-context §6（追加一行） | 任何 session |

### 旧文档保留还是覆盖

**保留（不删除）旧 spec/plan 文件**，因为：
- 旧文档记录了决策历史和"为什么"
- 有时需要回溯"这个决定是什么时候改的"
- 直接删除会让架构 session 失去上下文

**在 arch-context.md §6 标注版本变化：**
```
- 2026-XX-XX · 产品session · [功能名]设计从 vA 改为 vB，旧 spec: 2026-XX-XX-XXX.md
```

**新文档命名：** 日期在前，覆盖同一功能时用新日期，不删旧文件。
